# jumpserver-mcp 优化任务

## 背景
当前项目 `/home/lan/jumpserver-mcp` 是一个 JumpServer MCP Server，目的是让 AI 通过 SSH/SFTP 管理 JumpServer 纳管的资产。

## 当前状态
- 基于 FastAPI + fastapi-mcp（SSE 传输），核心逻辑在 `server.py`（707行单体文件）
- 提供 4 个自定义 MCP 工具：jumpserver_ssh_command / jumpserver_sftp_upload / jumpserver_sftp_download / jumpserver_sftp_list
- 另外通过 JumpServer OpenAPI swagger.json 自动生成大量 JumpServer API 工具（例如资产管理等）

## 用户需求
"目前只是为了调用 ssh 跟 sftp 使用" — 用户只需要 SSH/SFTP 功能，不需要那些自动生成的 JumpServer API 工具。

## 优化方向（请逐项分析并实现）

### P0：去除不必要的依赖
1. 启动时强制拉取 JumpServer swagger.json → 如果 JumpServer 不可达，服务完全无法启动。对于只需要 SSH/SFTP 的场景，这是多余的。
2. fastapi-mcp 的 OpenAPI→MCP 自动转换对 SSH/SFTP 场景完全没用，且引入了大量不必要的依赖和启动开销。
3. 分析：能否直接使用 `mcp` 库自带的 SSE transport，去掉 fastapi-mcp 依赖，简化架构？

### P1：连接复用（关键性能优化）
4. 当前每次 SSH/SFTP 调用都新建 paramiko 连接。
5. 建议：实现按 asset_ip+system_user 的 SSH 连接池，复用已有连接。
6. 注意：JumpServer 服务端 30 分钟无 IO 自动断连，连接池空闲超时设为 ~25 分钟即可，期间可通过心跳保持。
7. 连接池需要有最大连接数限制和空闲超时回收。

### P2：错误处理与可观测性
8. 当前错误返回纯字符串（如 "Error: SFTP 连接失败 - ..."），AI 难以结构化解析。
9. 建议：返回结构化 JSON，包含 success/error/code/message/data 字段。
10. 注：JumpServer 服务端已有审计日志，MCP 不需要重复实现审计。

### P3：安全与运维
11. SSH 命令执行超时应该可配置（当前硬编码 30s），且命令超时应区别于连接超时。
12. 添加命令白名单/黑名单模式（可选配置），防止危险命令（rm -rf /, shutdown 等）。
13. 支持 SSH 密钥认证（当前只支持密码）。

### 架构建议
14. 考虑将 server.py 拆分为：
    - `connection_pool.py` — SSH 连接池管理
    - `tools.py` — 4 个 MCP 工具的实现
    - `server.py` — 仅负责 MCP 服务端挂载
    - `audit.py` — 审计日志
15. app 启动改为纯 mcp SSE server，去掉 fastapi-mcp 的 OpenAPI 自动生成

## 约束
- Python >= 3.11
- 不要引入重量级框架
- 保持向后兼容（.env 配置格式不变，工具名称和参数不变）
- 所有修改完成后更新 README.md 和 docs/ai-mcp-ssh-usage.md
